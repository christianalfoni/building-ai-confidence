## Why the current setup is weird

The hidden `<div id="__initial_data__">` lives **inside** the React tree (inside `#root`). That single fact forces everything else:

- Because React owns that node during hydration, the client tree **must reproduce it identically** — same div, same stringified JSON — or React reports a hydration mismatch and discards/patches it. That's the *only* reason `entry-client.tsx` re-renders the div with `JSON.stringify(initialData)` again (lines 28-31). It's pure ceremony to keep React happy.
- So the data gets serialized twice (server + client) and the payload is something React diffs on every hydration, even though it's never meant to change.

The root cause: **server data shouldn't be part of the React tree at all.** It's a one-way handoff, not UI.

## The cleaner approach

Move the payload **out of `#root`** and write it directly to the HTML stream as a sibling, using a `<script type="application/json">` tag. React never sees it, so:

- No re-render on the client → delete the data div from `entry-client.tsx` entirely.
- No hydration mismatch possible → no need to re-stringify.
- The client reads it **once** before hydration, exactly as it does now.

```
<body>
  <script type="application/json" id="__initial_data__">{…}</script>  ← outside root, ignored by React
  <div id="root"><!--ssr-outlet--></div>
  <script type="module" src="/entry-client.tsx"></script>
</body>
```

`type="application/json"` means the browser neither executes nor renders it; it's inert until `entry-client` reads `.textContent` and `JSON.parse`s it — which is already what the client does.

### One important detail: escaping

Right now JSX auto-escapes the JSON's `<`/`>`/`&` as HTML entities, so the hidden div is accidentally XSS-safe. If we write the script tag as a **raw string** into the stream, we lose that, so a post containing `</script>` could break out. We'd escape `<` → `\u003c` (and ideally `\u2028`/`\u2029`) in a tiny helper before injecting. That's a small, well-understood function — and it actually makes the data handoff *more* robust than today, not less.

### Where to inject it

`entry-server` already splits the template on `<!--ssr-outlet-->`. The script just needs to be in the DOM before `entry-client` runs, so the natural spot is to prepend it to `htmlEnd` (the chunk after `</div>`, before the module script) — no new template placeholder needed, though adding an explicit `<!--ssr-data-->` marker would be more self-documenting. 

---

A variant worth a mention: instead of a JSON script tag you could emit `<script>window.__INITIAL_DATA__ = {…}</script>`. Slightly less ceremony on read (no `getElementById`/`JSON.parse`), but it executes JS and pollutes `window`. The JSON-script-tag approach is what I'd recommend (it's also what Next.js does with `__NEXT_DATA__`).
