## Research: Persisting & rendering images in posts

### How the system works today

- **Post body is raw markdown** stored in a single Postgres `TEXT` column (`posts.body` on Neon). `dbPostToPost` passes it through unchanged (`src/common/utils.ts`).
- **Editor** is CodeMirror 6 (`src/common/ui-components/MarkdownEditor.tsx`), code-split and SSR-safe. Extensions live in `src/common/markdown/editorExtensions.ts`. It already uses **block/line decorations** (for fenced code blocks and list indents) — the exact mechanism we'd reuse to render an image inline.
- **Reader** is `src/common/ui-components/Markdown.tsx` — it parses the same Lezer grammar and renders markdown **with markers kept visible** (`#`, `-`, ``` stay on screen). Crucially, **it renders text only — there is no `<img>` rendering anywhere today.** `![alt](url)` would currently show as literal characters.
- **Saving** goes through `useBlogEditor` (800 ms debounced) → `PATCH /api/posts/:id` (JSON only, auth via session cookie + `ALLOWED_LOGINS`).
- **No upload infrastructure exists**: no multipart middleware, no blob/S3/Cloudinary, no image columns. `@vercel/blob` is present only as a transitive lockfile entry, not a real dependency.

### Two separable problems

**1. Where the image bytes live (persistence)**
**2. How `![](url)` becomes a centered, non-clickable image in both editor and reader (rendering)**

---

### Persistence — recommendation: Vercel Blob

| Option | Verdict |
|---|---|
| **Vercel Blob** ✅ | Best fit. App already deploys via Vercel Build Output API. Add `@vercel/blob` + `BLOB_READ_WRITE_TOKEN`, create `POST /api/upload` (auth-gated like the other routes) that streams the file to blob and returns a public CDN URL. Store only the URL in the markdown body. Clean, cheap, fast, no DB bloat. |
| Base64 in `body` | Rejected. No infra, but inlining bytes bloats the `TEXT` column **and the SSR HTML payload** on every render — bad for performance even at a few images. |
| Neon `BYTEA` column | Rejected. Postgres is a poor blob store; needs a separate serving endpoint and bloats DB/backups. |
| S3 / Cloudinary | Rejected for now — more credentials and setup than needed when Vercel Blob is native. |

So: image lives in Vercel Blob, the post body just carries standard markdown `![](https://…blob…/file.png)`.

---

### The editor experience (drag-drop → centered, non-clickable)

- **Drop handling:** add a `drop` handler via CodeMirror `EditorView.domEventHandlers`. Use `view.posAtCoords(event)` to get the **exact cursor/drop offset**, upload the file to `/api/upload`, then insert `![](url)` at that offset. (Optionally show a placeholder like `![uploading…]()` and swap in the URL when the upload resolves.)
- **Inline render in the editor:** add a **block-widget decoration** (same pattern as the existing fenced-code decorations) that replaces an image-only line with a rendered `<img>` — centered, with vertical margins, `pointer-events: none` so it's not clickable/draggable-out.
- **Render in the reader:** extend `Markdown.tsx` to detect an image node on a line and emit a centered `<img>` instead of the literal text. This is the one genuinely new rendering path (the reader does no image rendering today).
- **Styling:** `display:block; margin: <space> auto; max-width:100%` + `pointer-events:none` satisfies "centered, with margins, not clickable."

### Open questions / risks

1. **`BLOB_READ_WRITE_TOKEN`** — needs to be provisioned (Doppler, per DEPLOYMENT.md) for prod and added to `.env.example`. Local dev without it would need a fallback or a disabled state.
2. **Validation** — restrict to image MIME types and a max size; decide what happens on failure.
3. **Image-only-line convention** — simplest rule is "a line that is just `![](url)` renders as an image." Do we need inline images mid-paragraph? (Recommend: no — keeps editor + reader decoration logic simple and matches the "centered block" UX you described.)
4. **Alt text** — drag-drop has no caption; default to empty alt or the filename.
5. **Paste-to-upload** — you only asked for drag-drop; paste is a cheap add-on later if wanted.

## Testing

Test files live next to the file they test, named `*.test.tsx` (or `.ts` for non-JSX files).

**Pattern for component tests:**

1. Import `createAppState` and `renderWithApp` from `src/test-utils`.
2. Create an `AppState` with mocked services using `createAppState({ ...only what this test needs... })`. `createAppState` wraps the instance with `reactive()` from `reactx` so that state mutations trigger component re-renders — this matches how `main.tsx` creates the live instance.
3. Optionally pre-mutate state before rendering (e.g. `appState.increment()`).
4. Call `renderWithApp(<ComponentUnderTest />, appState)` — this wraps the component in `AppContext.Provider`.
5. Interact via `@testing-library/user-event` and assert with standard `expect` matchers. DOM matchers like `toBeInTheDocument` are available globally via `@testing-library/jest-dom` (imported in `src/test-setup.ts`).

```tsx
import { screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { createAppState, renderWithApp } from "../test-utils";
import { Counter } from "./Counter";

describe("Counter", () => {

    const appState = createAppState();
    renderWithApp(<Counter />, appState);

    await userEvent.click(screen.getByRole("button", { name: /increment/i }));

    expect(screen.getByText("1")).toBeInTheDocument();
  });
});
```

# PR Workflow

Submit completed work as a pull request on GitHub.

## Steps

1. Check for unstaged changes with `git status`. If any exist, stage and commit them before continuing.

2. If a work folder exists for this branch (`work/YYYY_MM_DD_<branch-name>/`), capture agent sessions so they are included in the commit:
   ```bash
   ./scripts/capture-agent-sessions
   ```
   This writes one Markdown file per agent session into the branch work folder. If no work folder exists, skip this step.
3. Stage and commit changes using the conventional commit prefix that best fits:
   - `feat:` — new feature
   - `fix:` — bug fix
   - `chore:` — tooling, deps, config, scripts
   - `refactor:` — code change with no behaviour difference
   - `docs:` — documentation only
   - `test:` — tests only
   - `style:` — formatting, whitespace
4. Push the branch:
   ```bash
   git push -u origin <branch-name>
   ```
5. Validate before submitting:
   ```bash
   ./scripts/validate
   ```
   Fix any lint, type, or test failures before continuing.

6. Create or update the PR using MCP tools:
   - **No open PR exists:** call `mcp__github__create_pull_request` with `owner=christianalfoni`,
     `repo=building-ai-confidence`, `head=<branch>`, `base=main`, `title`, and `body`.
   - **Open PR exists:** call `mcp__github__update_pull_request` with `owner=christianalfoni`,
     `repo=building-ai-confidence`, `pullNumber=<number>`, `title`, and `body`.

   Use this template for the body:

   ```
   ## Current behavior
   ASCII diagram or screenshot showing how things worked before this change.

   ## New behavior
   ASCII diagram or screenshot showing what is different after this change.

   ## Assumptions
   Any assumptions made about intent, scope, or implementation that were not explicitly stated.

   ## Considerations
   Approaches explored, pivots made during implementation, or direction changes requested by the user.

   ## Validation
   How the change was verified — tests run, manual steps taken, or edge cases checked.

   ## Instructions followed
   Bullet list of the specific agent instructions (from CLAUDE.md or skills) that governed this change — so the reviewer can verify compliance.

   ## Work session
   This branch's plan and session artifacts are in `work/YYYY_MM_DD_<branch-name>/`. The plan documents the approach taken, tasks completed, and any deviations. GitHub Copilot can use this folder for context about the work session.
   ```

   The `Current behavior` and `New behavior` sections must visually represent the change — not prose. For UI changes, embed before/after screenshots using uploaded image URLs (see below). For non-UI changes, use ASCII diagrams with boxes, arrows, and flow notation.

   **Including screenshots in a PR:** If the change touches UI, take before/after screenshots using `./scripts/screenshot`, then generate links with:
   ```bash
   ./scripts/screenshot-url <before-name> <after-name>
   ```
   This prints a `[name](/path)` link for each screenshot. Paste the output directly into the PR body. Screenshot names may include or omit the `.png` extension.

   > **Note:** The Anthropic MCP proxy mangles `https://` URLs and HTML image tags in PR bodies, so screenshots are linked rather than inlined. Clicking a link opens the raw image on GitHub.

   Omit any section that has nothing meaningful to say (e.g. a brand-new feature has no "Current behavior").
7. Report the PR URL to the user.
8. After the PR is reviewed, resolve addressed threads with the `mcp__github__resolve_review_thread` MCP tool: fetch the thread node IDs via `mcp__github__pull_request_read` (`method: get_review_comments`), then call `resolve_review_thread` with `owner=christianalfoni`, `repo=building-ai-confidence`, and each `threadId`. Use the `/review` skill to apply feedback.

## Rules

- Never commit directly to `main`.
- One logical change per branch. If the plan covered multiple unrelated concerns, split them into separate branches.
- The PR title must follow the same conventional commit format as the commit message.
- Do not force-push a branch that already has an open PR unless the user explicitly requests it.
