## The two editing models

What you're describing is the difference between two fundamentally different approaches:

- **WYSIWYG / rich-text (TipTap, ProseMirror, Lexical):** You type `# Header` and it *disappears*, replaced by a rendered big heading. The document model is a rich tree, not text. This is the "conversion" you said you don't want.
- **Decorated source (CodeMirror 6):** The document stays as literal markdown text. `# Header` stays `# Header` on screen — but you can *paint* styling on top of it: color the `#`, make the heading text bigger, indent the `-` of a list, syntax-highlight a fenced code block, etc. The source text is never transformed; you just decorate it.

The second one is **exactly** what you described — "I want to actually write markdown... but the header should stay as is... bullets should still be hyphens but indented... code blocks styled and highlighted." This is the **live-preview** model, and it's literally how **Obsidian** works.

## The tool: CodeMirror 6

[CodeMirror 6](https://codemirror.net/) is the editor for this. The pieces you'd use:

- **`@codemirror/lang-markdown`** — parses the markdown into a syntax tree (via the Lezer parser) so the editor *knows* "this range is a heading, this is a list marker, this is a code fence."
- **Decorations** — you walk that tree and attach CSS classes / styles to ranges. This is the "freedom to choose how the markdown is transformed" you asked for — you decide that headings get a color, list markers get left-padding, etc. Nothing is forced.
- **`@codemirror/language` + a highlight style** — gives you the syntax highlighting *inside* fenced code blocks (and you can scope it so it only applies inside code, not to your prose).

So the answer to "is there a tool that lets me freely choose how markdown is styled while keeping it as markdown?" — yes, CodeMirror 6, and that's its core strength.

# Research: CodeMirror 6 as the article editor

## What the current editor is

The body editor today is a bare `contentEditable` `<div>` (no library) in `src/desktop/components/BlogEditor.tsx` and `src/mobile/components/BlogEditor.tsx`, driven by `useBlogEditor` (`src/common/hooks/useBlogEditor.ts`). It reads/writes `bodyRef.current.textContent` — a **plain string** stored in `DbPost.body`, auto-saved on an 800ms debounce. No markdown libs are installed. The reader view (`BlogPost.tsx`, both platforms) just splits `body` on `\n\n` and renders each chunk as a `<p>` — **no markdown rendering at all** today.

So the body is *already* a plain text string. Switching to CodeMirror means the stored value barely changes (it's still markdown-as-text); what changes is how it's displayed in the editor and in the reader.

## Is CodeMirror 6 the right tool? Yes — and all three behaviors are supported

CM6's model is "the document is plain text; you *decorate* it." That's precisely your "free to choose how the markdown is transformed" requirement. The building blocks: `@codemirror/lang-markdown` (parses markdown into a Lezer syntax tree), `@codemirror/view` Decorations, and `@codemirror/language` `HighlightStyle`.

### 1. Headers in a different color ✅ — easy
Use a `HighlightStyle` that maps the heading tags (`tags.heading1`, `heading2`, …) to colors via `syntaxHighlighting(...)`. Because CM6 only *styles* the text and never rewrites it, `# My header` stays literally `# My header` on screen — just colored. This is the simplest of the three and is essentially built-in once `lang-markdown` is loaded. You control every color in one style object. ([decoration example](https://codemirror.net/examples/decoration/), [syntax highlighting](https://deepwiki.com/codemirror/language/4.4-syntax-highlighting))

### 2. `- ` lists: indent but keep the hyphen ✅
Two separate pieces:
- **Continue the marker on Enter** — `@codemirror/lang-markdown` exports `markdownKeymap`, which binds Enter to `insertNewlineContinueMarkup`. Press Enter after `- foo` and you get a fresh `- ` on the next line. Because the source stays text, the marker **stays a hyphen** — there's no bullet conversion to opt out of (that only happens in WYSIWYG editors like TipTap). ([lang-markdown](https://github.com/codemirror/lang-markdown))
- **Visual indent** — add a *line decoration* (padding-left) to lines the syntax tree marks as `ListItem`. A small `ViewPlugin` that walks the tree and emits line decorations does this. The hyphen remains; the line just sits indented.

### 3. ` ``` ` code blocks: hide the fences, enter "code mode", highlight ✅ — most work
This is the involved one, done with two mechanisms, matching how Obsidian-style editors work:
- **Highlight code inside the fence** — `markdown({ codeLanguages: [...] })` accepts a set of languages (e.g. from `@codemirror/language-data`); CM matches the fence info string (` ```js `) and highlights the code with the real language grammar. ([lang-markdown](https://github.com/codemirror/lang-markdown))
- **Hide the backticks / "code mode" feel** — a `ViewPlugin` walks the tree, finds the `CodeMark`/fence nodes, and applies `Decoration.replace({})` (an atomic decoration) to hide them — *except* on the line the cursor is on, so you can still edit the fence. This "reveal around the cursor" pattern is exactly what [codemirror-rich-markdoc](https://github.com/segphault/codemirror-rich-markdoc) and [atomic-editor](https://github.com/kenforthewin/atomic-editor) do. ([hide markdown syntax thread](https://discuss.codemirror.net/t/hide-markdown-syntax/7602))

There are existing reference implementations (rich-markdoc, atomic-editor) we can borrow patterns from rather than inventing from scratch.

## Two things that need a decision

**A. SSR — must be client-only.** This app is server-rendered, and CM6 touches browser-only APIs (`navigator`) that throw in Node. The fix is standard and low-risk: the editor view is already an interactive, client-side-only screen (`app.view === 'editor'`), so we lazy-load the CM6 component (dynamic `import()` / `React.lazy`) and initialize inside `useEffect` so it never runs during SSR. ([SSR discussion](https://discuss.codemirror.net/t/server-side-rendering-for-read-only-codeblocks-in-cm6/4053))

**B. The reader side — the open question from before.** You said you want *readers* to "read it as markdown" too. Two viable routes, and we should pick before planning:
- **Reuse the same CM6 decorations in read-only mode** for the reader. Readers see the *identical* look to the editor (raw `#`, hyphens, hidden fences, highlighted code) with one styling definition shared by both. Most consistent with "I want it to stay as markdown," but readers get a code-editor surface rather than a typical article.
- **Render markdown → HTML for readers** (e.g. `react-markdown`) with CSS to match. More conventional published-article feel, SSR-friendly, but it's a *second* styling system to keep in visual sync with the editor.

My lean is the **first** (shared read-only CM6) because it directly matches what you described and avoids maintaining two renderers — but this genuinely changes the reading experience, so it's your call.

# Research report — final

## The key realization
Because the reader must show the **exact same surface** as the editor (visible `#`, hyphens kept, fences hidden, code highlighted), `react-markdown` is the *wrong* tool — it renders markdown to clean HTML and **strips** the markers. You'd then be fighting it to put the markers back, and constantly chasing visual parity between two unrelated renderers.

The right move is a **shared parser + one stylesheet** across editor and reader:

| | Editor (client only) | Reader (SSR) |
|---|---|---|
| Parser | `@codemirror/lang-markdown` (wraps the Lezer markdown grammar) | `@lezer/markdown` — the *same* grammar, standalone |
| Output | CM6 Decorations | walk the tree → React `<span>`s |
| Styling | **one shared CSS file** keyed on the same highlight classes | **same CSS file** |
| Highlight | CM6 `syntaxHighlighting` | `@lezer/highlight` `highlightTree` → same `tok-*` classes |

Both sides parse with the identical Lezer markdown grammar and emit the **same CSS classes**, so "look the same" is *guaranteed by construction*, not by manually keeping two styles in sync. ([@lezer/markdown](https://github.com/lezer-parser/markdown), [@lezer/highlight](https://github.com/lezer-parser/highlight))

## SSR is fully solved
- `@lezer/markdown` and `@lezer/highlight` are **pure JS, no DOM/`navigator`** — safe to run during SSR. The reader is fully server-rendered. ([static highlighting on the web](https://joelgustafson.com/posts/2022-05-31/syntax-highlighting-on-the-web/))
- CodeMirror never touches the server path — it only loads when you enter the client-only editor view (`app.view === 'editor'`), lazy-imported so it stays off the landing/post bundles.

## How each of your three behaviors lands

1. **Headers in a different color** — one `HighlightStyle`/CSS rule on the heading tag. Editor and reader both keep the `#`, both colored, from the same CSS. ✅ easy
2. **`- ` lists: indent, keep the hyphen** — Editor: `markdownKeymap` continues the `- ` on Enter (no bullet conversion exists to fight); a line decoration adds the indent. Reader: the `ListItem` span gets the same indent class. Hyphen stays on both. ✅
3. **` ``` ` code blocks: hide fences, code mode, highlight** — Editor: `Decoration.replace` hides the backticks (revealed around the cursor), `codeLanguages` highlights the code. Reader: the fence marks get a `display:none` class, the code tokens get the same highlight classes. Identical result, no cursor-reveal needed on the reader. ✅ (the bulk of the work)

## What changes in the codebase
- **Storage:** unchanged — `DbPost.body` stays a markdown string.
- **Reader:** `BlogPost.tsx` (desktop + mobile) stops doing the `\n\n`→`<p>` split and instead renders the shared markdown component.
- **Editor:** `BlogEditor.tsx` (desktop + mobile) swaps the `contentEditable` div for the CM6 component; `useBlogEditor` keeps its debounce/save but reads from CM's doc instead of `textContent`.
- **New shared module:** the markdown styling lives in one place (the CSS + the tree-walk → spans for the reader, the decorations for the editor) so both trees and both platforms reuse it.
- **New deps:** `@codemirror/*` (state, view, language, lang-markdown, commands) + `@lezer/markdown` + `@lezer/highlight`, plus code-language grammars for whatever languages you want highlighted.

## Risks / open points
- **Code highlighting languages:** decide which languages to support in fences (each adds a grammar/bundle). Easy to start with a handful (js/ts/json/bash) and grow.
- **The fence "code mode" reveal logic** is the fiddliest part (cursor-aware decoration). Reference implementations exist ([rich-markdoc](https://github.com/segphault/codemirror-rich-markdoc), [atomic-editor](https://github.com/kenforthewin/atomic-editor)).
- **`@codemirror/lang-markdown` was archived Apr 2026** (moved to `code.haverbeke.berlin`); npm still works — we'll confirm we pull the maintained line. `@lezer/markdown` itself is active.
