# Todo App

## Summary
Replace the counter example with a single-list todo app. Todos are stored in localStorage and support add, complete/incomplete toggle, inline edit, and delete. The app loads persisted todos on startup and syncs every change back to storage automatically.

## Considerations

- **Storage abstraction:** Rather than calling `localStorage` directly from `AppState`, add a `storage` service to the `Services` interface. This keeps state logic testable via a fake in-memory implementation and follows the established services → state pattern.
- **Data model:** Each todo is `{ id: string; text: string; completed: boolean }`. IDs are generated with `crypto.randomUUID()` — no external dependency needed.
- **Editing state:** The "which todo is being edited" is transient UI state, not domain state. It lives in the `App` component as a `useState` value rather than in `AppState`.
- **localStorage key:** A single `"todos"` key stores the full serialised array. Simpler than per-item keys and avoids key enumeration.
- **Reusable ui-components:** The add input and inline edit input share styling, so an `Input` ui-component is warranted. The checkbox and icon-only delete/edit buttons are distinct enough to also be their own components (`Checkbox`, `IconButton`).
